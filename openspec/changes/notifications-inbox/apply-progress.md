## Deviations from Design

1. **Detail-fetch failures: inline microcopy only, not a toast** — tasks.md's task 4.2 bullet lists "a failed mark-unread/delete/detail-fetch shows a sonner toast.error(...)" as one item, but design.md's D7 explicitly separates these: "Mutation failures (open-mark-read, toggle, delete) call `toast.error`... Detail load failure shows inline pane microcopy" (a distinct, deliberate choice — "the row or pane may already have moved on, so a toast survives the re-render" is D7's stated rationale specifically for *mutations*, not detail loads). I implemented per D7: mark-read/mark-unread/delete failures → `toast.error` + optimistic rollback; a failed `GET [id]` → inline `NotificationEmptyPane variant="error"` using `copy.pane.loadError`, no toast. Flagging this because tasks.md and design.md read as contradictory on this one point; I followed the design (the more authoritative, explicitly-reasoned source) rather than silently picking one.
2. **`NotificationPaneState` has no "error" value, but `NotificationEmptyPane`'s variant prop does** — design.md's Interfaces/Contracts block defines `NotificationPaneState = "empty" | "loading" | "ready" | "notFound"` (4 values, task 0.1 says implement "per design.md's Interfaces/Contracts block" verbatim) but `NotificationEmptyPane`'s own Props line lists `variant: "empty" | "notFound" | "error"` (3 values, a different enum). I did not add a 5th value to `NotificationPaneState`. Instead, the hook exposes an additional (design-silent, but not design-contradicting) `loadError: boolean` flag alongside the existing `paneState`, and the client combines `paneState === "notFound"` + `loadError` to choose between the `"notFound"` and `"error"` pane variants. This satisfies both interfaces exactly as specified without extending either.
3. **Two extensions to the hook's public return type not in design's Interfaces block**: `anchor: number | null` and `clear(): void` (alongside the specified `open`/`step`/`close`/`updateSelected`). These were needed to implement D2 (delete-advance) correctly — `close()`'s "call `history.back()` if pushed" semantics are wrong for a *programmatic* delete-triggered clear when there's no next item, so a parallel unconditional-replace `clear()` was added. `anchor` is exposed so the client can resolve the next item against the fresh list returned directly from the delete's own refetch response, avoiding a stale-closure read of hook state one render tick behind. Neither addition changes or contradicts any documented interface; both are additive.
4. **Prev/Next also mark the target item read** — not explicitly stated in design.md's Testing Strategy row for the hook, but follows directly from the Data Flow section's `open(id): ... if unread → PATCH {isRead:true}` applying uniformly whenever selection resolves to a new id (list click, Prev/Next, deep link, popstate) — Gmail-style convention, consistent with D2's own justification ("email-client convention"). Implemented via the hook's `onResolved` callback (added post-review as part of the 6.3 lint fix — see Issues Found #3), which fires from every resolution path uniformly, rather than a client-side effect.
5. **`onResolved?: (notification) => void` added to the hook's args (not in design's Interfaces block)** — added post-review (Issues Found #3) to move the "mark read on open" side effect out of a `useEffect` in the client and into a plain callback invoked from within `resolve()`. Purely additive to the args type; doesn't change `UseNotificationSelectionResult`.
6. **`NotificationDialog`'s `DialogTitle`/`DialogDescription` are sr-only, separate from the visible heading (D9)** — the coordinator's instruction says "DialogTitle = notification title," which I initially read as "use Radix's `DialogTitle` component as the visible heading." That would require `NotificationReadingPane`/`NotificationEmptyPane` to render `DialogTitle`/`DialogDescription` directly — but Radix's `Dialog.Title`/`Dialog.Description` call `useDialogContext` internally and **throw** if rendered outside a `Dialog`, which would have broken every existing standalone unit test for those two components (they'd all need wrapping in a real `<Dialog open>` context). Instead, `NotificationDialog` (the wrapper) renders a sr-only `DialogTitle`/`DialogDescription` pair itself (props `title`/`description`, computed by the caller), satisfying Radix's `aria-labelledby`/`aria-describedby` wiring, while the *visible* heading stays a plain `<h2 ref={titleRef}>` inside `NotificationReadingPane`/`NotificationEmptyPane` — unchanged in kind from before, just re-purposed to also receive `onOpenAutoFocus`'s focus. Net effect: the dialog's accessible name is the notification's title (satisfying the letter of the instruction), the visible heading is unchanged, and every existing component-level test kept working without modification to its rendering harness. Flagging this as a deviation from a literal reading of "DialogTitle = notification title" (as in, the literal component), not from the *intent* (an accessible title matching the notification's title).
7. **Error variant shows no separate body text** — `NotificationEmptyPane`'s `error` variant has only `copy.pane.loadError` as its title; there's no distinct body string for it (unlike `notFound`, which has both `notFoundTitle` and `notFoundBody`). Rather than duplicate `loadError` as both title and body text (visually repeating the same sentence) or add a new dict key for a body no one asked for, the `error` variant renders no body paragraph — the dialog's sr-only `DialogDescription` (reusing `loadError` too) already covers the accessible-description requirement.

## Issues Found (and fixed)

1. **Bug: infinite mark-read/unread retry loop.** An effect that auto-marked the opened item as read was keyed on `selection.selected` object *identity*. Since `markUnread`'s optimistic update (and its rollback on failure) also creates a new `selected` object for the *same* id, the effect kept re-firing `markRead`, which itself optimistically flips `isRead` back, which re-fires the effect — looping forever on a failed PATCH (caught by a real test timeout, not a silent bug). Originally fixed with an id-keyed ref guard (`autoMarkedIdRef`); that whole effect was later removed as part of the 6.3 lint fix below (superseded by the `onResolved` callback, which structurally can't re-fire on `updateSelected`'s in-place patches since it's only invoked from `resolve()`). Saved to Engram (`getrandomtrip`, "Fixed infinite mark-read/unread loop in notifications reading pane").
2. **Real typecheck bug caught early**: the PATCH route's audience query param was passed straight into Prisma's `where.audience` as a raw `string`, which doesn't satisfy Prisma's generated `NotificationAudience` enum type. Fixed by routing it through the existing `parseNotificationAudience()` helper (same one `GET` and the list routes already use).
3. **Lint errors this change introduced, fixed (post-review)**: scoping `eslint` to only this change's touched files (rather than the noisy full-repo `npm run lint`) surfaced 3 `react-hooks/set-state-in-effect` errors + 1 unused-`eslint-disable` warning in `useNotificationSelection.ts`, plus 1 more `set-state-in-effect` error in `RoleNotificationsPageClient.tsx` that I had incorrectly filed under "pre-existing repo debt" in my first pass instead of fixing. All fixed without `eslint-disable`, using React's recommended alternatives:
   - `useNotificationSelection.ts`'s two effects that derived `anchor` from `list`/`selectedId`/`page`/`status` were replaced with in-render "adjust state when a prop changes" comparisons (https://react.dev/learn/you-might-not-need-an-effect#adjusting-some-state-when-a-prop-changes) — each guarded by its own stored "previous value" (`prevPageStatusKey`, and a `prevList`/`prevSelectedIdForAnchor` pair), mirroring exactly what the removed effects' dependency arrays used to gate on. The mount-effect's `latest = selection` test-harness assignment (`react-hooks/globals`) was moved into a `useEffect`. Two `ref.current = x` assignments that were mutating refs during render (`react-hooks/refs`) were moved into small dedicated effects.
   - **A real regression during the fix**: my first attempt at the anchor-derivation adjustment re-derived `anchor = idxInList` unconditionally whenever the item was still present in `list` — with no gate on whether `list`/`selectedId` had actually changed. This meant that on a page/status change (which should reset the anchor to `null`), the *same* render that reset it would also immediately re-derive it back to the old index (since the item was still technically present in the still-referentially-identical `list` used by that specific test) — undoing the reset. The existing "resets anchor to null on page or status change" hook test caught this immediately (went red). Fixed by gating the idx-tracking adjustment behind an explicit `list !== prevList || selectedId !== prevSelectedIdForAnchor` check, restoring the same "only re-derive when these specific inputs changed" semantics the original effect's dependency array provided implicitly.
   - `RoleNotificationsPageClient.tsx`'s auto-mark-read effect (watching `selection.selected`, calling `markRead`) was removed entirely. Mark-read-on-open is now triggered via an `onResolved` callback passed into `useNotificationSelection`, invoked directly inside the hook's `resolve()` function for every successful resolution path (list hit, snapshot hit, `GET [id]`) — never from `updateSelected`'s in-place patches, so the original infinite-loop bug class (Issues Found #1) can no longer occur by construction, not just by a guard. Since `onResolved` is declared before `markRead` exists (to keep `useNotificationSelection`'s call site above `markRead`'s definition, which itself depends on `selection.updateSelected`), a `markReadRef` ref bridges the two — set once via a small effect (`markReadRef.current = ...`, a ref assignment, not a `setState` call, so it isn't flagged either).
   - Verified via strict TDD: ran the existing 14 hook tests + 12 client tests **first** (both green), confirming no observable behavior change was required before touching lint; only added no new tests since none were needed.
   - Result: `npx eslint` on all 22 changed/untracked `.ts`/`.tsx` files in this change → **0 errors, 0 warnings**. Repo-wide `npm run lint` still fails with 62 pre-existing errors across ~35 files this change never touches (down from 65 before this fix, since 3 of the fixed instances happened to be counted in that repo-wide run too) — that remainder is genuinely pre-existing baseline debt (`eslint-config-next@16.2.6`'s newer React-Compiler-aware `react-hooks/*` rules flagging long-standing patterns in files like `ThemeProvider.tsx`, `useTripRequests.ts`, `AccountSettingsPanel.tsx`, `LanguageContext.tsx`), out of scope for this change, and correctly left unfixed and unclaimed by task 6.3.
4. **Two remaining pre-existing `eslint-disable` comments, removed (D9 round)**: the D9 instructions raised the bar from "0 errors/0 warnings" to "0 errors/0 warnings, **no `eslint-disable`**" — stricter than Follow-up 1's fix, which had left 2 `eslint-disable-next-line react-hooks/exhaustive-deps` comments in place (both legitimate at the time — genuinely suppressing warnings, not "unused"). Removed both with real dependency-array fixes instead of suppression:
   - `useNotificationSelection.ts`'s mount-effect for `initialSelectedId` used an empty `[]` dep array (intentionally, to run only once) with a disable to silence the resulting warning about `initialSelectedId`/`resolve` not being listed. Fixed with a `didInitialResolveRef` ref guard: the effect now lists its real dependencies (`[initialSelectedId, resolve]`) honestly, and the ref ensures the actual resolve call still only ever fires once, even if either dependency's identity changes on a later render.
   - `RoleNotificationsPageClient.tsx`'s delete-advance effect depended on `[notifications]` only, deliberately excluding `selection` (whose `canNext`/`step`/`clear` it reads) with a disable, so the effect wouldn't re-run on every unrelated render (`selection` is a new object every render).
